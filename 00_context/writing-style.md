# 글쓰기 스타일

내 글을 대신 쓰거나 다듬을 때 따르는 기준.

## 핵심 원칙

- 결과만 나열하지 않고 이유와 메커니즘을 쓴다.
- 의사결정은 트레이드오프 중심으로. 무엇을 택하고 무엇을 포기했는지 드러낸다.
- 기본값이나 외부 제약으로 한 선택을 능동적 설계처럼 포장하지 않는다.
- 표준적인 배경 설명은 압축하고, 내가 겪은 문제와 판단은 충분히 풀어 쓴다.
- 시행착오나 아직 확인하지 못한 영역은 매끈하게 숨기지 않고 그대로 남긴다.
- 애매한 형용사는 수치, 조건, 사례로 바꾼다.
- 긴 문장은 자르되 인과관계는 남긴다.
- 문체를 매끈하게 만들려고 개성을 제거하지 않는다.
- 종결어미: 문장형 글은 습니다체로 통일하되 과거형 어미만 반복하지 않고 현재형과 의문형을 섞어 문장 끝 호흡이 겹치지 않게 한다. 목록·MR/PR·커밋 문구는 개조식 명사형 종결, 대화형 메모는 짧고 직접적인 문장.

## AI 티 금지

AI가 썼다는 티가 나는 요소는 쓰지 않는다.

| 금지 | 예 | 대신 |
| --- | --- | --- |
| em dash 기호 `—` | `A설명 — 가나다라` | 쉼표, 마침표, 콜론으로 문장을 나눈다 |
| 괄호 부가설명 | `A설명(가나다라 부가설명)` | 중요하면 문장으로 풀고, 아니면 뺀다 |
| 행정 문서투 한자어 | `A 신설, B 수립` | 새로 추가, 정함 같은 일상어 |
| AI 상투어 | `다양한 개선을 통해 성능을 효율적으로 향상` | 구체적 사실과 수치 |
| 근거 없는 평가어 | `강력한 캐싱으로 뛰어난 속도 확보` | 근거를 대거나 뺀다 |
| 번역투 피동·명사화 구문 | `~가 수행되었습니다`, `~를 가능하게 합니다` | `~했습니다`, `~할 수 있습니다`처럼 능동형 동사로 직접 서술 |
| 기계적 접속사 나열 | 문장마다 `또한,`, `아울러,`, `더불어,`, `결과적으로,`로 시작 | 접속사를 빼고 앞뒤 문장의 인과관계로 바로 연결 |
| 상투적 대조 구문 | `단순히 A가 아니라 B라는 점에서 의미가 있습니다` | 수식 구조 없이 핵심 사실 B만 바로 서술 |
| 서론·결론의 포장형 요약 | `이번 작업을 통해 ~의 중요성을 확인했으며 앞으로도 ~할 예정입니다` | 할 말이 끝나면 교훈이나 다짐 없이 바로 문단 종료 |

## im-not-ai 윤문

사용자가 im-not-ai 윤문을 요청하거나 "AI 티 안 나게 해줘"처럼 말하면 im-not-ai의 humanize-korean 스킬로 점검하고 걷어낸다. 모든 문장형 산출물에 자동으로 돌리는 게 아니라 사용자가 원할 때 쓰는 권장 도구다.

## 문장 고치기 예시

위 규칙을 기반으로 이 예시를 학습해 문장을 쓰고 고친다. 실제 글 샘플은 계속 보강한다.

### 개조식: 목록·MR/PR·커밋

#### 고치기 전

> 자료 정리 절차 신설: 분류 기준 수립 — 다양한 요청을 통해 효율적으로 개선(담당자 지정 포함)

#### 고친 후

> 자료 정리 절차 추가: 자료 찾는 데 오래 걸린다는 요청이 많아 분류 기준을 정하고 담당자를 지정.

### 문장형: 문서·트러블슈팅·배경 설명

#### 고치기 전

> 캐시 레이어 도입을 통해 데이터베이스 부하를 성공적으로 절감하고 응답 속도를 크게 향상시켰습니다. 또한 다양한 만료 정책을 검토하여 최적의 아키텍처를 수립했습니다(초기 설정 복잡도 증가 포함).

#### 고친 후

> 조회 API 응답이 2초 넘게 걸려 Redis 캐시를 붙였습니다. 정합성 맞추기가 까다로워지는 문제가 있지만, 지금 당장 DB CPU 사용률을 낮추는 게 급해 TTL 5분짜리 단순 캐싱만 먼저 적용했습니다.

## 셀프 체크

- 내가 실제로 쓸 법한 문장인가?
- em dash, 괄호 부가설명, 행정 문서투 한자어, 번역투 피동 표현이 남아 있는가?
- 모든 문장이 `~했습니다`로 똑같이 끝나거나 `또한`, `아울러` 같은 접속사가 반복되지 않는가?
- 글 마지막에 불필요한 다짐이나 요약 문단이 붙어 있지 않은가?
